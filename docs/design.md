# Shade design and implementation reference

This guide describes the current implementation in the source tree: how the shell boots, how its main surfaces are composed and placed, and which theme primitives they use. It is a source-derived reference, not a promise about behavior inferred from historical specifications or screenshots. Any rationale is labelled separately from implementation facts.

## Runtime composition

The shell’s source-linked dependency flow is:

- [`apps/shell/src/main.ts`](../apps/shell/src/main.ts) starts the shell application, initializes logging and translations, and installs graceful signal handling.
- [`apps/shell/src/App.tsx`](../apps/shell/src/App.tsx) defines the `Adw.Application`, registers application actions, and invokes `boot()` for a local UI launch. A remote command-line invocation is routed to `requestHandler` instead of mounting a second UI.
- [`packages/widgets/src/index.tsx`](../packages/widgets/src/index.tsx) re-exports the composition root. Its import of [`packages/widgets/src/bootstrap.ts`](../packages/widgets/src/bootstrap.ts) loads the built-in service and widget declarations for their registration side effects.
- [`packages/core/src/define.ts`](../packages/core/src/define.ts) collects those declarations; `boot()` then initializes settings, initializes services, wires widget callbacks, and renders each non-lazy widget.
- Shutdown disposes the mounted widget trees and then the registered services through [`packages/core/src/serviceRegistry.ts`](../packages/core/src/serviceRegistry.ts).

`defineService()` and `defineWidget()` are the registration boundary. Service modules declare their instances and optional dependencies / initialization arguments; widget modules declare a name, mount function, optional actions, and optional lazy status. Imports are therefore part of the dependency graph: a widget’s imports bring in the services it uses, while ES-module caching prevents a shared module from registering twice. At boot, service initialization follows dependencies and order weights; widget actions are merged and later passed to `ShellState`, keeping shell state independent of widget imports. See [`define.ts`](../packages/core/src/define.ts), [`ServiceRegistry`](../packages/core/src/serviceRegistry.ts), and the boot sequence in [`bootstrap.ts`](../packages/widgets/src/bootstrap.ts).

### Boot and lifecycle order

1. The app constructor calls `ShellState.registerCommands()` and registers command actions exposed by other services. These are `Gio.SimpleAction`s on the application; for example, `ShellState` provides `toggle-applauncher`, `toggle-quicksettings`, `toggle-windowswitcher`, `toggle-settings`, `toggle-clipboard`, `open-clipboard`, `lockscreen`, and `close-all` in [`shellState.ts`](../packages/services/src/state/shellState.ts). The default Hyprland shortcuts for common actions are defined in [`nix/hyprland/binds.nix`](../nix/hyprland/binds.nix).
2. The widget import graph registers built-in services and widgets. `boot()` calls `initSettingsRoot()` before service initialization so schema accessors are usable, builds an `AppContext` containing the application and `ServiceRegistry`, and calls `initServices()`.
3. `boot()` registers collected widget callbacks on `ShellState`, then mounts every declared non-lazy widget independently. A failure in one widget’s render is logged without preventing the remaining widgets from mounting. The Settings widget is deliberately lazy; its action calls `openSettings()` and renders the `Adw.PreferencesWindow` on demand.
4. The root app retains widget disposers. On shutdown it runs them, then calls `ServiceRegistry.disposeAll()`; the registry disposes services in reverse initialization order. These paths are implemented in [`App.tsx`](../apps/shell/src/App.tsx), [`bootstrap.ts`](../packages/widgets/src/bootstrap.ts), and [`serviceRegistry.ts`](../packages/core/src/serviceRegistry.ts).

### State, actions, and events

`ShellState` owns transient shell state such as launcher visibility/query, Quick Settings visibility, and the lock flag; these are reactive GObject properties, not a single persistent preferences object. Its public methods toggle or close those states and emit shell events where other domains need to react. The single typed bus instance in [`packages/services/src/bus.ts`](../packages/services/src/bus.ts) combines domain event contracts for shell, capture, system notifications, input, audio, display, power, time, network, and search. `ShellState.init()` subscribes to lock/unlock and close requests. Widget action callbacks are registered from the composition root, rather than imported directly into the service.

`WindowManager` is a registry for live windows, not the owner of their rendering: it keeps collections for per-monitor bars, wallpapers, and lockscreens and slots for single surfaces such as Quick Settings, OSD, launcher, notifications, Settings, and dock. The registry is defined in [`packages/services/src/state/windowManager.ts`](../packages/services/src/state/windowManager.ts); window components register and unregister themselves.

### Settings and service ownership

Settings schemas are declared near their domain. [`packages/core/src/settingsRegistry.ts`](../packages/core/src/settingsRegistry.ts) provides `defineSettings()`, which declares a GSettings schema and returns a lazy typed accessor; `initSettingsRoot()` instantiates the groups at shell boot. Service and widget modules import their own accessors rather than reaching through a global settings context, as described by [`packages/services/src/settings/index.ts`](../packages/services/src/settings/index.ts).

For example, the general schema is shared from `core` because appearance and weather-derived values are consumed by several services; the bar schema is owned by the bar domain and consumed by the bar, dock, and Settings UI. See [`general.gschema.ts`](../packages/core/src/settings/general.gschema.ts) and [`bar.gschema.ts`](../packages/services/src/settings/bar.gschema.ts). A settings control’s concrete effect is implemented by its owning page or service; the existence of a GSettings-backed control alone does not imply that all controls share identical immediate or persistence behavior.

## Separate application entry points

The greeter and screen/window share picker are separate programs, not shell widgets or Settings pages:

- [`apps/greeter/src/main.ts`](../apps/greeter/src/main.ts) starts a standalone `Gtk.Application` for greetd and renders `Greeter` from [`greeter-ui/index.tsx`](../apps/greeter/src/greeter-ui/index.tsx), which creates its own Astal window. It does not call the shell widget composition root.
- [`apps/share-picker/src/main.ts`](../apps/share-picker/src/main.ts) starts a separate `Gtk.Application` for the XDPH share-picker flow. It builds monitor and window sources, presents a GTK window with Screens, Windows, and All tabs, and provides Cancel; [`ui.ts`](../apps/share-picker/src/ui.ts) constructs the cards and tabs. It is not mounted by `packages/widgets/src/bootstrap.ts`.

## Navigation, focus, and transient-surface coordination

The default Hyprland bindings expose `SUPER+Space` for the launcher, `SUPER+n` for Quick Settings, `SUPER+Tab` for the switcher, `SUPER+,` for Settings, and `SUPER+Shift+V` for clipboard mode; see [`binds.nix`](../nix/hyprland/binds.nix). These invoke registered GActions rather than raw D-Bus examples. The action names come from `ShellState` and the other services registered by [`App.tsx`](../apps/shell/src/App.tsx).

The launcher is the search-first pattern: becoming visible restores the ShellState query, focuses the entry, and updates its results; hiding clears the query and emits the close event. Clipboard mode uses `>` as the launcher query/mode marker in `ShellState`. The switcher is a keyboard-first pattern: it grabs focus on opening, consumes its navigation keys, and closes after selection. Settings is a separate, lazy `Adw.PreferencesWindow` with libadwaita’s built-in Preferences search rather than a layer-shell panel. Its open/focus/recreate path is in [`settingsOpen.ts`](../packages/widgets/src/settings/settingsOpen.ts).

There is no single exclusivity manager for every transient surface. In particular, launcher and Quick Settings close each other only when the bar is vertical, where their side-anchored geometry can compete; the source implements these checks in both surface visibility handlers. `ShellState.closeAll()` closes the launcher, Quick Settings, and switcher, not every shell window. The switcher and lockscreen explicitly use exclusive keyboard mode; the launcher and shared popups use on-demand keyboard mode, while the capture overlay also explicitly uses on-demand mode. Those are separate from layer-shell exclusive zones. See [`shellState.ts`](../packages/services/src/state/shellState.ts), [`applauncher/index.tsx`](../packages/widgets/src/applauncher/index.tsx), [`quicksettings/index.tsx`](../packages/widgets/src/quicksettings/index.tsx), [`windowswitcher/index.tsx`](../packages/widgets/src/windowswitcher/index.tsx), and [`PopupWindow.tsx`](../packages/widgets/src/common/PopupWindow.tsx).

## Visual system and adaptive layout

### Implemented styling

The shell uses GTK4/libadwaita primitives and standard Adwaita CSS variables. `Theme` installs a user-priority CSS provider and maps its five palette inputs in [`packages/style/src/theme.ts`](../packages/style/src/theme.ts):

| Palette field | Adwaita variable |
|---|---|
| `bg` | `--window-bg-color` |
| `fg` | `--window-fg-color` |
| `primary` | `--accent-bg-color` and `--accent-color` |
| `surface` | `--card-bg-color` |
| `shadow` | `--shade-color` |

The current generator also sets `--accent-fg-color` to white. `Theme` selects the active stylesheet’s light or dark palette according to `Adw.StyleManager`; with no active stylesheet it uses its Adwaita-inspired light/dark defaults. These are native Adwaita variables, including the standard `--shade-color`; this implementation does not emit legacy custom `--shade-*` token families.

The appearance page offers Auto, Light, and Dark. [`ColorScheme`](../packages/services/src/display/colorScheme.ts) stores that choice in general settings, resolves Auto from the weather-derived day/night state, and pushes the resolved `prefer-light` or `prefer-dark` preference to `org.gnome.desktop.interface`. The [`Wallpaper`](../packages/widgets/src/wallpaper/index.tsx) surface chooses the day image in Auto daytime or Light mode and the night image in Auto nighttime or Dark mode.

Dynamic theming is optional. [`PaletteGenerator`](../packages/style/src/palette.ts) checks for the `matugen` executable, watches the dynamic-theming preference and wallpaper setting changes, and runs Matugen against the configured day wallpaper when enabled. It parses Matugen light and dark color maps, maps `background`, `on_background`, `primary`, `surface_container`/`surface`, and `shadow` into the five palette fields, then activates a `matugen` stylesheet through `Theme`. Disabling dynamic theming removes that active stylesheet and returns to the base palette. The Appearance UI shows an install hint if Matugen is unavailable; a regenerate request also warns and returns when the binary is missing. The relevant control and service code is in [`appearance.tsx`](../packages/widgets/src/settings/appearance.tsx), [`palette.ts`](../packages/style/src/palette.ts), and [`theme.ts`](../packages/style/src/theme.ts).

Surfaces use native classes such as `card`, `background`, `linked`, `compact`, `round`, `suggested-action`, `destructive-action`, and `error`, and use symbolic icon names such as `network-wireless-symbolic`, `camera-photo-symbolic`, and `alarm-symbolic`. `@window_bg_color` and the palette variables are consumed directly in widget styles. The project’s [GTK4 + libadwaita theming reference](STYLEGUIDE.md) catalogs the supported CSS variables, classes, sizing properties, and reusable patterns; use it as the token catalog rather than inventing a parallel palette.

`packages/widgets/src/common/index.ts` is the shared component surface for `QuickToggleButton`, `IconButton`/`IconMenuButton`, `ActionButton`, `Slider`, `AudioEndpointControl`, `LinkedBox`, `IconInfoRow`, `Notification`, `PowerMenu`, weather components, and popover cleanup. Widget roots compose these domain-independent controls into larger surfaces; see [`common/index.ts`](../packages/widgets/src/common/index.ts).

### Verified orientation and monitor adaptations

- The bar turns its `Gtk.CenterBox` and each content group vertical when positioned on the left or right, and horizontal when positioned on the top or bottom. It creates one window per monitor. [`bar/index.tsx`](../packages/widgets/src/bar/index.tsx)
- Launcher and Quick Settings follow the focused Hyprland monitor. Their widths account for monitor scale, keep edge margins, and reserve width for a vertical bar; launcher and Quick Settings have separate calculations. [`applauncher/index.tsx`](../packages/widgets/src/applauncher/index.tsx), [`quicksettings/index.tsx`](../packages/widgets/src/quicksettings/index.tsx)
- Shared popups derive anchors and margins from the configured bar edge. Wallpaper and lockscreen create per-monitor windows; recording boundary windows are also created per monitor. [`common/PopupWindow.tsx`](../packages/widgets/src/common/PopupWindow.tsx), [`wallpaper/index.tsx`](../packages/widgets/src/wallpaper/index.tsx), [`lockscreen/index.tsx`](../packages/widgets/src/lockscreen/index.tsx), [`recording-boundary/index.tsx`](../packages/widgets/src/recording-boundary/index.tsx)
- Quick Settings uses a vertical scrolling composition on narrow available widths; the launcher and switcher keep their search/list structures within monitor-aware windows. These dimensions and anchors come from source calculations, not a claim that every physical display will produce identical geometry.

### Design rationale (interpretation, not an additional behavior contract)

The implementation’s use of Adwaita classes and system color variables favors recognizable controls and a shared visual language over a separate custom token system. Edge-anchored, monitor-aware panels keep shell controls near the configured bar; centered search/switcher content gives launcher and switching different layout roles. The explicit keyboard modes also suggest a deliberate distinction between ordinary popups and surfaces that need full keyboard ownership (the switcher and lockscreen). These are design readings of the code above, not extra runtime guarantees.
